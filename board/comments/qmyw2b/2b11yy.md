Ruling: `<key>-<id>` is the reference token in prose, on the same board
as well as across boards. The bare id survives only inside the
frontmatter keys `parent`, `depends_on` and `related`, where the key
name already says what the value is. `oif:<key>/<id>` stays the identity
for `resource` and `about.resource`, and is not a prose token.

`oif:` was rejected on a mechanical finding rather than taste. GitHub
permits `:` and `/` in an autolink prefix, but its alphanumeric suffix
matcher accepts only letters, digits and hyphen — not `/`. So a prefix
of `oif:` would stop matching at the slash and link `oif:app` alone, and
a per-board `oif:app/` prefix cannot coexist with `oif:` because
prefixes may not overlap. The URI form therefore autolinks worse than
the token form while costing twice the typing.

Two syntaxes is not a defect. Every tracker that works separates a typed
handle from a resolvable identifier: `PROJ-123` beside a browse URL,
`#412` beside an issues URL, a DOI beside doi.org. The conversion here
is mechanical in both directions.

A parser hazard came out of the same analysis: a filename stem such as
`fix-login-7k2x9m` contains a false token `login-7k2x9m`. Section 5.1
now forbids extracting tokens from paths or from text preceded by a
hyphen, a slash or an alphanumeric.

Consequences: `key` moves from OPTIONAL to RECOMMENDED, since a board
without one has no prose token and no `resource`, and the validator now
warns when it is absent. The change is additive — the reference regex
already accepted both forms, so no existing board, schema or published
package breaks.

An autolink is configured on this repository with the prefix `oif-`, so
`oif-qmyw2b` resolves in issues, pull requests and commit messages.
